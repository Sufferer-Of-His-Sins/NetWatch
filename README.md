# NetWatch — система мониторинга сетевого оборудования

## 1. Описание

Необходимо разработать клиент-серверную систему мониторинга парка сетевых устройств (роутеры, коммутаторы, ONT) с собственным протоколом. Агенты, эмулирующие устройства, периодически отправляют метрики на центральный сервер. Сервер сохраняет данные в PostgreSQL, определяет «упавшие» устройства и рассылает тревоги операторам. Оператор работает через консольный клиент.

### Компоненты

| Компонент | Назначение |
|---|---|
| `agent` | Эмулирует сетевое устройство, отправляет метрики |
| `server` | Принимает агентов и операторов, проверяет пороги, рассылает тревоги, работает с БД |
| `operator` | Консольный клиент оператора |
| `postgres` | Готовая СУБД, запускается в Docker-контейнере (не разрабатывается) |

### Схема

```
 ┌─────────┐   metrics / heartbeat   ┌──────────┐      libpq       ┌──────────────┐
 │ agent 1 │ ──────────────────────> │          │ ───────────────> │  PostgreSQL  │
 ├─────────┤                         │  server  │                  │   (Docker)   │
 │ agent N │ <────── command ─────── │          │                  └──────────────┘
 └─────────┘                         │          │ ──── alert ─────> ┌──────────┐
                                     └──────────┘ <─── query ────── │ operator │
                                                                    └──────────┘
```

## 2. Техническое задание

### 2.1. Общие требования

- Язык: C, ОС: Linux (Ubuntu).
- Сетевое взаимодействие agent/operator ↔ server: сокеты `AF_INET`, TCP.
- Работа с БД: библиотека `libpq` (`libpq-dev`), только параметризованные запросы (`PQexecParams`).
- Сборка: Make или CMake, бинарники складываются в `bin/`.
- Собственная система логирования: уровни DEBUG / INFO / WARN / ERROR, вывод в файл и в консоль, метка времени, имя компонента.
- Консольный интерфейс у сервера и у оператора.
- Конфигурация сервера (порт, параметры подключения к БД, максимум клиентов, таймаут heartbeat) через файл или переменные окружения. Пароль БД в код не зашивается.
- Корректное завершение по `SIGINT` / `SIGTERM`: закрытие сокетов, закрытие соединения с БД, запись в лог.
- Сервер обслуживает не менее 50 одновременных агентов и нескольких операторов (`epoll` или потоки).
- Сервер не падает и не зависает, если БД недоступна: ошибка пишется в лог, соединение восстанавливается автоматически.

### 2.2. Агент

- При старте регистрируется на сервере, передавая `device_id`, тип устройства и версию прошивки.
- Раз в N секунд (настраивается) отправляет метрики:
  - загрузка CPU, %;
  - использование RAM, %;
  - uptime;
  - входящий и исходящий трафик по портам;
  - состояние портов (up/down).
- Значения генерируются случайно, но правдоподобно: плавный дрейф, редкие всплески.
- Принимает команды от сервера: `set_interval`, `reboot` (эмуляция: разрыв связи и повторная регистрация), `get_status`.
- Отвечает на heartbeat.

### 2.3. Сервер

- Принимает регистрацию агентов, ведёт таблицу устройств: online/offline, время последнего сообщения.
- Устройство считается offline, если heartbeat не приходил дольше T секунд. Сервер генерирует тревогу `device_down`.
- Проверяет метрики по правилам. Пример: CPU > 90 % три замера подряд даёт тревогу `high_cpu`.
- Сохраняет устройства, метрики и тревоги в PostgreSQL.
- Рассылает тревоги всем подключённым операторам.
- Пересылает команды оператора нужному агенту и возвращает результат.
- Имеет консольный админ-интерфейс: список подключений, статистика, состояние соединения с БД, изменение порогов.

### 2.4. Оператор

Консольное меню:

1. Список устройств и их статусов.
2. Детали устройства (последние метрики).
3. История метрик за период.
4. Журнал тревог.
5. Отправка команды устройству.
6. Live-режим: тревоги приходят в реальном времени.

Оператор к БД напрямую не обращается, все данные получает через сервер.

### 2.5. База данных (PostgreSQL)

- Используется готовый образ `postgres:16`, запуск через `docker-compose`.
- Схема создаётся автоматически при первом старте из `database/init.sql`.
- Данные хранятся в Docker volume и переживают перезапуск контейнера.
- Вложенные данные (состояние портов) хранятся в колонке типа `JSONB`, остальное в обычных колонках.

`docker-compose.yml`:

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: netwatch
      POSTGRES_PASSWORD: netwatch
      POSTGRES_DB: netwatch
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./database/init.sql:/docker-entrypoint-initdb.d/init.sql
volumes:
  pgdata:
```

`database/init.sql`:

```sql
CREATE TABLE devices (
    device_id   TEXT PRIMARY KEY,
    type        TEXT,
    firmware    TEXT,
    online      BOOLEAN NOT NULL DEFAULT FALSE,
    last_seen   TIMESTAMPTZ
);

CREATE TABLE metrics (
    id          BIGSERIAL PRIMARY KEY,
    device_id   TEXT NOT NULL REFERENCES devices(device_id),
    ts          TIMESTAMPTZ NOT NULL,
    cpu         REAL,
    ram         REAL,
    uptime      BIGINT,
    ports       JSONB
);
CREATE INDEX idx_metrics_device_ts ON metrics (device_id, ts);

CREATE TABLE alerts (
    id          BIGSERIAL PRIMARY KEY,
    device_id   TEXT,
    kind        TEXT NOT NULL,
    ts          TIMESTAMPTZ NOT NULL DEFAULT now(),
    details     JSONB
);
CREATE INDEX idx_alerts_ts ON alerts (ts);
```

Необходимые операции: добавление и обновление устройства, вставка метрик, выборка последних метрик устройства, выборка истории за период, вставка и выборка тревог.

### 2.6. Протокол agent/operator ↔ server

Кадрирование: 4 байта длины (big-endian) + JSON-тело. Это решает проблему разбиения и склейки пакетов в TCP.

```
+----------------+---------------------------+
| length (4 B)   | JSON body (length bytes)  |
+----------------+---------------------------+
```

Типы сообщений:

| type | направление | назначение |
|---|---|---|
| `register` | agent → server | регистрация устройства |
| `register_ack` | server → agent | поля `status` (ok/error), `reason` |
| `metrics` | agent → server | пакет метрик |
| `heartbeat` / `heartbeat_ack` | двусторонний | проверка связи |
| `command` | server → agent | команда агенту |
| `command_result` | agent → server | результат (`status`, `reason`) |
| `alert` | server → operator | тревога |
| `query` / `query_result` | operator ↔ server | запрос данных |

Пример пакета метрик:

```json
{
  "type": "metrics",
  "device_id": "sw-014",
  "ts": 1790000000,
  "cpu": 37.5,
  "ram": 61.2,
  "ports": [
    {"id": 1, "state": "up", "rx": 1200, "tx": 800}
  ]
}
```

### 2.7. Тестирование

- Модульные тесты протокола: сериализация, разбор, обрезанный пакет, склеенные пакеты.
- Тесты слоя БД (нужен запущенный контейнер `postgres`): вставка, выборка, обновление.
- Интеграционный тест: сервер + 10 агентов, проверка, что тревоги доходят до оператора и записи появляются в БД.
- Скрипт нагрузочного теста, поднимающий 50 агентов.
- Проверка отказоустойчивости: остановка контейнера БД во время работы, затем запуск. Сервер продолжает работать и восстанавливает соединение.

## 3. MVP (минимально жизнеспособный продукт)

MVP считается достигнутым, если выполнено всё из списка:

- [ ] PostgreSQL запускается командой `docker compose up -d`, схема создаётся автоматически.
- [ ] Один сервер, один тип агента, один оператор; связь по TCP с кадрированием (длина + JSON).
- [ ] Агент регистрируется и шлёт `metrics` и `heartbeat`.
- [ ] Сервер поддерживает несколько агентов одновременно и определяет online/offline по таймауту.
- [ ] Реализовано одно правило тревоги: `device_down`.
- [ ] Устройства, метрики и тревоги сохраняются в PostgreSQL через `libpq`.
- [ ] Оператор может:
  - [ ] посмотреть список устройств со статусами;
  - [ ] посмотреть последние метрики устройства;
  - [ ] получать тревоги в live-режиме.
- [ ] Логирование в файл и в консоль.
- [ ] Makefile собирает все бинарники, есть хотя бы один тест протокола.
- [ ] README с инструкцией: установка `libpq-dev`, запуск БД, сборка, запуск.

**Не входит в MVP:** команды агентам, история за период, пороги по метрикам, автоматическое переподключение к БД, аутентификация, TLS, деплой сервера в Docker.
